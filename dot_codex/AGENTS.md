## 1. 基本方針

- すべての対話は日本語で行う。
- 英語のドキュメント、コード、エラーメッセージ、ログは原文のまま扱う。
- docstring や code comment は、プロジェクトの既存方針がなければ英語を優先する。
- 不明点があっても、安全に仮定できる場合は仮定を明示して進める。
- 仕様・安全性・データ破壊・外部コストに関わる不明点は、実行前に短く具体的に確認する。

## 2. 作業の進め方

- まず関連ファイル、既存実装、テスト、README、設定ファイルを確認して、最小限の変更範囲を把握する。
- 軽微な修正、明確なバグ修正、ドキュメント変更では、永続的な計画ファイルを作らない。
- 通常はチャット内で 2〜5 行程度の短い方針を示してから進める。
- 複雑、曖昧、高リスク、または複数ステップにまたがる作業では、実装前に簡潔な計画を示す。
- 計画は原則としてチャット内に留める。
- `plans.md`、`PLANS.md`、その他の計画ファイルは自動作成しない。
- ユーザーが明示した場合、またはプロジェクトに既存の計画運用がある場合のみ、指定された計画ファイルを使う。

## 3. 計画ファイルの扱い

### 3.1 通常時

- `plans.md` を新規作成しない。
- `plans.md` が既に存在していても、ユーザーが明示しない限り更新しない。
- 進捗記録のためだけにファイルを増やさない。
- 必要な進捗共有は、チャット内の簡潔な報告で行う。

### 3.2 ExecPlan / PLANS.md

- ユーザーが「ExecPlan」「PLANS.md を使う」「長期計画を作る」と明示した場合のみ使用する。
- 大規模機能、重要なリファクタ、移行、複数時間にわたる作業では、既存の `PLANS.md` または `.agent/PLANS.md` があるか確認する。
- 新しい計画ファイルを作る必要がある場合は、作成前に目的、保存先、含める内容を簡潔に提示して確認する。
- ExecPlan を使う場合でも、実装中にむやみに別の計画ファイルを作らない。

## 4. セーフティ / ガードレール

- 本番環境への書き込み、デプロイ、データ削除、マイグレーション、課金発生、外部 API の大量実行は、明示的な許可なしに実行しない。
- 破壊的操作を行う前に、目的、影響範囲、代替案、rollback 方法を簡潔に提示する。
- 秘密情報、API キー、トークン、個人情報を生成・貼り付け・平文保存しない。
- `.env`、認証情報、秘密鍵、ローカル資格情報を必要なく読み取らない。
- 新しい依存関係を追加する場合は、理由、代替案、リスクを説明する。
- ネットワークアクセス、外部サービス、MCP、ブラウザ操作は、必要性が明確な場合のみ使う。
- sandbox や approval の制約を回避しない。必要な場合はユーザーに確認する。

## 5. 実装方針

- 最小差分で実装する。
- 既存の設計、命名、スタイル、エラーハンドリング、ログ方針に合わせる。
- 不必要な大規模リライト、整形だけの巨大 diff、無関係な修正を避ける。
- 関連する既存ユーティリティ、型、テストヘルパーを優先して再利用する。
- 変更の理由が伝わるように、必要な箇所だけコメントを追加する。
- コメントは「何をしているか」よりも「なぜ必要か」を説明する。
- 依存更新は、セキュリティ、互換性、機能要件など明確な理由がある場合に限る。

## 6. テスト / 検証

- 実装変更では、関連するテストを追加または更新することを原則とする。
- 既存のテスト、lint、format、typecheck コマンドが分かる場合は、変更範囲に応じて実行する。
- すべてのテストを実行する必要はない。変更に対して十分な検証を選ぶ。
- テストを実行できない場合は、理由と未検証リスクを最終報告に明記する。
- ドキュメントのみ、コメントのみ、設定の軽微な変更では、テスト不要な場合がある。
- バグ修正では、可能な限り再現テストまたは回帰テストを追加する。

## 7. コマンド実行

- コマンドは既存の package manager、Makefile、task runner、README の手順を優先する。
- 不明な場合は、`package.json`、`pyproject.toml`、`Makefile`、`justfile`、`README` などから推測する。
- 破壊的・高コスト・長時間・ネットワーク依存のコマンドは、事前に確認する。
- 依存インストールや lockfile 更新は、必要性を確認してから行う。
- コマンド失敗時は、原因を要約し、次の最小アクションを提示する。

## 8. Git / 差分 / レビュー

- ユーザーが明示しない限り、commit、push、branch 作成、PR 作成は行わない。
- 最終報告では、変更ファイル、主な変更内容、実行した検証、未検証事項を簡潔にまとめる。
- レビュー前に diff を確認し、不要な変更、デバッグ出力、秘密情報、破壊的変更が含まれていないか確認する。
- コミットメッセージを求められた場合は Conventional Commits を優先する。
  - 例: `feat: ...`, `fix: ...`, `docs: ...`, `refactor: ...`, `test: ...`

## 9. 出力品質

- まず動く最小解を優先する。
- 改善案は、実装後または明示的に求められた場合に提示する。
- 長い説明よりも、変更点、理由、検証結果、リスクを簡潔に伝える。
- 実装提案では、必要に応じて diff 形式を使う。
- ユーザーがレビューしやすい単位で変更する。
- 既知の制約や不確実性は隠さず明記する。

## 10. プロジェクト固有ルールの優先順位

- より近い階層の `AGENTS.md` または `AGENTS.override.md` がある場合は、その指示を優先する。
- README、CONTRIBUTING、既存コード、テスト、CI 設定の実態を尊重する。
- このファイルとプロジェクト固有ルールが矛盾する場合は、より具体的で近い指示を優先する。
- 矛盾により安全に進められない場合のみ、ユーザーに確認する。

## 11. やらないこと

- ルーチン作業のために `plans.md` を作らない。
- 毎回 AGENTS.md の要約を出さない。
- チェックポイントごとに不要な承認待ちをしない。
- 無関係なファイルを整形・修正しない。
- テストや検証をしたふりをしない。
- 秘密情報を読まない、保存しない、出力しない。
- sandbox や approval を無断で弱めない。

## 1. 会話言語

- すべての対話は日本語で行う。
- 英語のドキュメント・コード・エラーメッセージは原文のまま扱う。docstring や comment は英語が好ましい。
- 不明点や曖昧な指示がある場合は、短く具体的に質問してから行動する。

## 2. 進め方

- 作業を始める前に、影響範囲を評価し、広い・不確実性が高い場合は **計画を作成** する。
- 計画は通常 `plans.md` に記述するが、指定がある場合は **Kiro の Spec**（`.kiro/specs/<slug>/{requirements,design,tasks}.md`）を計画として採用する。

  - Goal / Scope / Approach / Risks / Checkpoints / Rollback / Artifacts

- 以下のプロセスを守る：

  1. **計画の作成** — 実装前に計画をまとめる。
  2. **承認の取得** — 計画（`plans.md` または Kiro Spec）が確認・承認されるまで実行を保留する。
  3. **実行** — 各 Checkpoint ごとに進捗を報告し、次の指示を待つ。
  4. **検証と報告** — 結果を確認し、必要に応じて改善案を提示する。

### 2.1 Kiro Specs モード（オプトイン）

以下のいずれかに該当する場合、**Kiro Specs モード**で進める：

- ユーザーが「Kiro を使う」「.kiro を参照して進めて」と明示した場合
- Issue/PR/タスクに **Kiro Spec Slug**（例：`refactor-masking-logic`）が指定されている場合

Kiro Specs モードでは、`.kiro/specs/<slug>/` 配下の

- `requirements.md` → **Goal / Scope / Acceptance**
- `design.md` → **Approach / Risks / Rollback（該当時）**
- `tasks.md` → **Checkpoints / Artifacts**
  を **計画の正** とみなす。`plans.md` の新規作成は不要。

実行前に以下を満たすこと（チェックリスト）：

- `requirements.md` に目的・非対象・受入基準が記載されている
- `design.md` に影響範囲とリスクが明記されている
- `tasks.md` に **順序立てられたタスク** と **チェックポイント** がある
- 破壊的/コスト影響がある場合、**Rollback** の記載がある

不備がある場合は、差分最小で追記提案（diff）を行い、承認後に実行する。

### 2.2 ExecPlans

When writing complex features or significant refactors, use an ExecPlan (as described in .agent/PLANS.md) from design to implementation.

## 3. セーフティ / ガードレール

- 本番環境への書き込みは禁止。実施する場合は明示的な許可とロールバック手順を提示する。
- 秘密情報（API キー、トークン、個人情報など）を生成・貼り付け・平文保存しない。
- 破壊的操作（削除、大規模リライト、スキーマ変更、課金発生）は、実行前に代替案とリスクを説明する。
- 外部 API の利用時はコスト・上限・権限を事前確認する。
- **Kiro Specs モードでも同様**。Spec に未記載の場合は `design.md` に追記（diff）して承認を得る。

## 4. 出力品質

- 最小で動作する解をまず示し、その後に改善案（可読性・保守性・パフォーマンスなど）を提示する。
- 変更提案には差分（diff）、根拠、テスト観点を含める。
- ドキュメントやコマンド手順は 1 コマンドで再現可能な形にまとめる。
- Kiro Specs を採用している場合、**成果物リンクやログの格納先** を `.kiro/specs/<slug>/artifacts/`（存在しなければ作成）に整理する。

## 5. テスト

- 作成・修正を行った場合、テストを必ず追加または更新する。
- テストの種類（単体・統合・E2E）はプロジェクト側のポリシーに従う。

## 6. コーディング規約

- スタイルツール（例: ruff, eslint, rustfmt）を優先する。
- コミットメッセージは Conventional Commits に従う（例: `feat: ...`, `fix: ...`, `docs: ...`）。
- 依存更新を行う場合は、理由（セキュリティ、機能追加、バグ修正）とリスクを記載する。

## 7. 変更提案の流れ

1. 課題を要約し、制約と目的を整理する。
2. `plans.md` に計画を記述し、承認を得る。**Kiro 指定時は `.kiro/specs/<slug>/` を計画として承認**する。
3. 実装を小さな単位で行い、テストを同梱する。
4. レビュー前に安全性・可読性・運用・コストの観点で自己確認を行う。

## 8. plans.md の扱い

- 各タスクに紐づく計画は `plans.md` に記載する。**ただし Kiro 指定時は `.kiro/specs/<slug>/` を計画として扱う**。
- 最終版はコミットして履歴管理・監査対象とする。
- ドラフトを別ファイルに分ける必要はない。

## 9. ツール / 実行ポリシー

- コマンドは目的・前提・期待結果を簡潔に書く。
- 生成 AI の提案は必ず検証し、根拠や公式ドキュメントを参照する。
- 依存バージョンは必要に応じて明記する（e.g., Python >=3.12, Node >=20）。
- **Kiro Specs モード時**：実行前に `requirements.md`・`design.md`・`tasks.md` の **要約** を提示し、齟齬がないかワンショットで確認する（往復は最小）。

## 10. plans.md のフォーマット例（必ずしもこの形式に従う必要はない）

```md
# plans.md

## Goal

目的を簡潔に記述。

## Scope / Non-Goals

含める範囲 / 除外する範囲。

## Approach

実行ステップを小さく分割。必要なら Checkpoint を設定。

## Risks & Mitigations

主要リスクと緩和策。

## Checkpoints

C1, C2, C3 ... の通過基準を記載。

## Rollback

戻し方と条件（Optional）。

## Artifacts

関連 PR やドキュメントリンクなど（Optional）。
```

## 11. 行動方針

- 作業開始前に、この AGENTS.md およびプロジェクト側 AGENTS.md・plans.md を読み、要約する。
- 実装提案は最小差分（diff）形式で提示する。
- 危険な操作やコストの高い操作は、実行前に計画へ追記し、承認を得る。（**Kiro 使用時は `design.md` に追記**）
- 回答は簡潔にまとめ、詳細は必要に応じて分割する。
- ユーザーが **「Kiro を使う」** と明示したタスクでは、`.kiro/specs/<slug>/` の内容を **一時的な計画ソース** として扱う。
  - `.kiro/specs/` は **コミット不要**。短期的な実行計画（ephemeral plan）として扱う。
  - 実行後、重要な決定事項やリスクは **plans.md に反映** して履歴を残す。
  - `.kiro/specs/` 内の `requirements.md`・`design.md`・`tasks.md` を自動的に読み取り、整合性を確認してから実行する。
  - 不備（Rollback未記載・リスク不明など）がある場合は、diff 形式で修正提案を行い、承認後に実行する。

### 11.1 Kiro Tasks の扱い

- `tasks.md` のチェックボックス（`- [ ]` / `- [x]`）は、**実行進行状況を直接反映** するための唯一の編集対象とする。
- 各タスク実行後は、自動または手動で該当項目を `[x]` に変更し、進行を記録する。
- 編集対象は **チェックボックス行のみ**（内容本文・設計書・要件には変更を加えない）。
- `tasks.md` はコミット不要だが、進捗共有が必要な場合は一時的に差分（例: diff 形式）で提示してよい。
- 進行状況は AI エージェントが随時参照し、どのタスクが未完了・完了済みかを把握する。
- 進行中に気づいた改善点・懸念点は `design.md` にコメント形式で追記する（例: `<!-- NOTE: ... -->`）。

### 11.2 実行フロー（Kiro Tasks モード）

1. `.kiro/specs/<slug>/tasks.md` を読み込む
2. チェックボックスの状態をスキャンし、未完了タスクを上から順に実行候補とする
3. 実行するタスクごとに:
   - 対応する要件（requirements.md の該当項目）を確認
   - 該当する設計ステップ（design.md の該当ブロック）を参照
4. 実行が完了したら、その行の `[ ]` を `[x]` に変更
5. すべてのタスク完了後、主要な変更点・気づきを `plans.md` に要約して残す

## 12. 注意事項

- 計画を飛ばして直接実装しない（Plan-first）。
- 自動化に依存しすぎず、最終判断は人間が行う。
- 「動いたら OK」で終わらせず、テストとドキュメント更新までを含める。
- Kiro 指定がない場合は従来通り `plans.md` を用いる（デフォルト）。
- Kiro 指定がある場合でも、**最終的な成果や教訓は `plans.md` に要約** して残す。
- `.kiro/specs` ディレクトリは一時的なワークスペースとして扱い、Git 管理しない。
  - 実装完了後は自動的に削除またはアーカイブされることを想定。
